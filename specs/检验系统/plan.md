## 2. 现有系统现状分析

### 2.1 后端（poct-lis）

**已实现（配置层 — 基础数据管理）**：

| 模块 | 表 | 状态 |
|------|-----|------|
| 检验分组 CRUD | `lis_inspection_group` | ✅ 完成 |
| 检验项目 CRUD | `lis_test_item` | ✅ 完成 |
| 仪器管理 CRUD | `lis_comm_instrument` | ✅ 完成 |
| 诊疗项目 CRUD | `lis_charge_item` | ✅ 完成 |
| 质控管理（8个子模块） | `lis_qc_*` | ✅ 完成 |

**未实现（工作流层 — 检验核心流程）**：

| 代码缺失 | 对应表 | 业务影响 |
|----------|--------|----------|
| 样本/检验单管理 | `lis_inspection_sample` | 🔴 无样本接收、无检验单 |
| 检验结果管理 | `lis_inspection_result` | 🔴 无结果录入/展示 |
| 报告单管理 | `lis_inspection_report` | 🔴 无报告生成/发布 |
| 医嘱接口 | `his_requisition` | 🟡 无 HIS 对接入口 |
| 仪器-项目关联 | `lis_test_item_group` | 🟡 仪器无法关联具体项目 |
| 基础字典 | `lis_base_data` | 🟡 科室/标本等字典无管理界面 |
| 修改日志 | `lis_change_log` | 🟢 审计追溯缺失 |
| 收费明细 | `lis_charge_item_charge` | 🟢 诊疗项目收费无明细 |
| 诊疗项目-分组关联 | `lis_charge_item_group_rel` | 🟡 多对多关系未映射到代码 |

> **核心发现**: 当前系统只实现了"字典/配置管理"，完整的检验工作流（申请→采集→接收→检测→审核→报告）完全没有代码。

## 3. 实施路径分析

### 3.1 优先级评估框架

```
优先级 = 业务依赖关系 + 实现难度 + 价值密度

P0（阻塞性）：后续功能依赖此模块，必须最先实现
P1（核心价值）：检验系统的核心业务价值
P2（增强体验）：提升可用性和完整性
P3（远期规划）：非一期必需
```

## 5. 风险评估

| # | 风险 | 概率 | 影响 | 缓解措施 |
|---|------|------|------|----------|
| 1 | `lis_inspection_sample` 表字段过多(95+) | 高 | 代码臃肿，维护困难 | 考虑拆分为 PatientInfo、SampleInfo 等 VO 分层 |
| 2 | DDL 缺少主键和 FK 约束 | 高 | 数据一致性问题 | Phase 1 添加主键索引 + 应用层校验 |
| 3 | BACKEND Entity PK 类型不统一 | 中 | 映射错误 | instrument_id 用 VARCHAR(20)，test_item_id 用 BIGINT — 需统一 |
| 4 | 前端类型定义 PK 为 string 而实际为 Long | 中 | 运行时类型错误 | Phase 1 修正所有 types.ts |
| 5 | 设备采集协议多样 | 高 | 开发周期不可控 | Phase 0.5 先做协议调研 + 抽象层设计 |
| 6 | HIS 对接依赖外部系统 | 高 | 无法独立测试 | Mock HIS 服务 + 中间表方案作为降级 |

## 6. 技术决策

| # | 决策点 | 选择 | 理由 |
|---|--------|------|------|
| 1 | 状态管理 | 利用现有 `inspection_state` 字段 | DDL 已有该字段，避免新增状态表 |
| 2 | 审核流程 | 状态枚举 + Service 层状态机 | 简单可控，不需引入工作流引擎 |
| 3 | 危急值检测 | 结果保存时 AOP 拦截 | 不侵入业务代码，可独立测试 |
| 4 | HIS 对接协议 | RESTful 优先，HL7 适配器可选 | 现代 HIS 普遍支持 REST |
| 5 | 报告模板 | Phase 7 引入，一期用固定模板 | 模板设计器开发周期长 |
| 6 | 仪器通道管理 | 新增 2 张关联表 | DDL 现有设计无独立通道表 |
| 7 | 字典管理 | 复用 `lis_base_data` 多态设计 | class_id 区分类型，无需新建多张表 |
